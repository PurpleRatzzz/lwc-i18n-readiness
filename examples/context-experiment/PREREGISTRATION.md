# Context experiment: preregistration

Committed **before** any translation was run. The results file states every deviation from this plan.

## Question

The scanner's rule R6 asks for translator context in Custom Labels. Does that context change AI translation quality? And are sentence fragments fixed by context alone, or do they need restructuring?

## Two sets of material

### Set 1, dreamhouse (main result)

Real hardcoded strings from `trailheadapps/dreamhouse-lwc` at `3f496e4`, taken from the human-reviewed gold set ([eval/gold/dreamhouse.csv](../../eval/gold/dreamhouse.csv)) and externalized as Custom Labels:

- **15 single strings**: buttons, input and slider labels, card titles, alt text, toasts, an error message, an empty state and an instruction.
- **5 real sentences that the code assembles from pieces**: `{n} days on <br/>the market`, `Distance to property: {n} miles`, `Beds: {x} - Baths: {y}`, `{n} items • page {p} of {t}`, `Click <b>Scan QR Code</b> to open…`.

[dreamhouse/design.json](dreamhouse/design.json) gives, for each string, its gold-set id, its source line, and where it appears in the UI. **The context comes from the component code.**

### Set 2, starter kit (secondary: labels whose usage is unknown)

The 23 Custom Labels of `salesforce/offline-app-developer-starter-kit` at `fb66da8`, as they exist in that repo.

No code in that repo's full history, and nothing found by GitHub code search, uses these labels. So the C2 context and the judging scenario (a mobile record list with search, sort, a filter panel and toasts) are **reconstructed from the label set**, not observed. See [starterkit/design.json](starterkit/design.json).

This set shows what happens when a translator has no usable context and can only guess, and how much inferred context changes. It is reported separately and may be left out of the conclusions. `FSL_LMR_Test` ("Test Label") is in the files but not scored.

## Conditions (same for both sets)

Same English values, same translator, same settings. Only what the translator is told changes.

| | What each label carries |
|---|---|
| **C1, as found** | Dreamhouse: `shortDescription` = the value and no categories, the practice found in 13 of 23 starter-kit labels. Starter kit: the original file, unchanged. Fragments are separate labels (`days on`, `items`, `of`…). |
| **C2, context** | Same labels. `shortDescription` and `categories` follow R6: the UI element, what it does, the sentence a fragment belongs to, and `maxlen` for short UI text. |
| **C3, context and structure** | C2, but each sentence that code assembles from pieces becomes one label with placeholders, e.g. `{0} items • page {1} of {2}`. |

The files are generated by [make-conditions.mjs](make-conditions.mjs).

## Translator and isolation

- **One translator for everything.** Project A's pipeline, through B's command translator: `--content-type ui`, default config E, target `zh-CN`. The same translator runs every condition of both sets, and each condition is run once. [run.sh](run.sh) records A's commit, whether its working tree had local changes, the model ID, and the time in `runs/run-info.json`.
- **Isolated from the question setter.** A runs as a separate process and receives only the exported XLIFF file (the English source plus the `<note>`s). It never sees the design files, the reconstructed scenario, these expectations, or the session that wrote them. The notes contain no Chinese and no hints at a "right" translation.
- **Judged by a person.** The question setter writes no verdicts.

## Judging

- **Judge**: Yanlin Chen, native zh-CN speaker and localization PM.
- **Blind**: each text is shown with its UI position and the English the user would see, but not its condition. Within a set, units from all conditions are shuffled together with a fixed seed. The key is kept in a separate file and opened only after judging.
- **Unit**: the text a user sees.
  - The single strings: 15 for dreamhouse, 16 for the starter kit.
  - The assembled sentences: 5 for dreamhouse, 4 for the starter kit. In C1 and C2 they are judged as the code would assemble them from the translated pieces, with example numbers filled in. In C3 they are judged as the one translated label, with the same numbers.
  - That makes 20 units per condition per set, 120 judgments in total.
- **Verdict**: *acceptable* means it would ship as is in that UI position in a Salesforce zh-CN product. Anything else is *not acceptable*.
- **Error type** (one main type per unacceptable unit):
  - `meaning`: wrong sense or part of speech, e.g. "Property" as 属性 instead of a house
  - `order`: the assembled text has unnatural word order
  - `terminology`: wrong term or register for Salesforce zh-CN UI
  - `placeholder`: a placeholder or markup is broken
  - `length`: over `maxlen` where one is given
  - `other`

The judging sheets and the scoring come from [judge.mjs](judge.mjs).

## What will be reported

- Per set: acceptable units per condition (out of 20), and error types per condition.
- The number of units A's QA gate sent to human review, per condition.
- Every source string, translation and verdict.
- No significance test: with n = 20 per condition this is a demonstration, not a measurement. Results are reported even if context makes no difference.

## Expectations, written down before the run

1. **C2 ≥ C1.** Any difference should come from strings whose meaning depends on context:
   - Dreamhouse: `Property picture` (a house, not an attribute), `Search Key`, `Bedrooms` (a minimum on a slider), `Reset`.
   - Starter kit: `Filter`, `Select`, `None`, `Enabled`/`Disabled`, `Search`.

   Many strings (`Success`, `Cancel`, `Save`) will be acceptable without context.
2. **Fragments.** In C1 and C2, assembled sentences will often be unacceptable however good the context, because the code fixes the English word order and spacing (`page {p} of {t}`, `{shown} items of {total}`). C3 should fix most of them.
3. **Starter kit, C1 vs C2.** The gain should be at least as large as for dreamhouse, because its C1 descriptions give even less to go on. Since its scenario is reconstructed, that gain shows the value of context for a translator who otherwise has to guess, not the value of the "right" context.
